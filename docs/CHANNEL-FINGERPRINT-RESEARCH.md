# 渠道校验处理调查

本调查始于2026-10-23，讨论WorkBuddy的11128请求拒绝及相关开源实现。各项目的机制及状态按当时资料记录，现有插件规则需核对所用提交。

## 1. 调查对象

WorkBuddy错误信息可能涉及消息文本、会话标识和首条消息。消息内容对照需要记录角色、位置和具体请求字节。客户端提示名称本身不足以确定某一次拒绝的匹配条件。

本项目的请求准备位于 `src/upstream.ts`，重试位于 `src/shim.ts`，CLI调用位于 `src/cli-bridge/runner.ts`。

## 2. 方案类别

| 类别 | 实现方式 | 需要核对的条件 |
| --- | --- | --- |
| 官方CLI调用 | 由已安装的客户端程序发送请求 | 程序来源、权限、上下文和计费 |
| 内容处理 | 按已知规则转换提示文本 | 修改范围、是否重复修改同一文本、缓存表现及网关的字符处理 |
| 请求协议适配 | 按接口要求构造请求头和结构 | 实测依据、版本和完整性要求 |
| 客户端识别 | 根据协议标识路由流量 | 标识的稳定性与来源 |

这些类别对应不同产品的接口条件，采用前应在具体请求链中验证。

## 3. 公开材料

原调查参考CLIProxyAPI的Claude Cloak、AIRoute的处理文档，以及BitRouter从提示前缀改为协议标识的记录。

- [CLIProxyAPI PR #868](https://github.com/router-for-me/CLIProxyAPI/pull/868)
- [AIRoute处理说明](https://github.com/jaccen/AIRoute/blob/main/docs/security/STEALTH_GUIDE.md)
- [BitRouter PR #594](https://github.com/bitrouter/bitrouter/pull/594)
- [客户端请求标记文章](https://thereallo.dev/blog/claude-code-prompt-steganography)

这些材料记录不同协议上的实现，本文将其作为比较来源。

## 4. 诊断摘要

原问题摘要最多显示4条消息，且曾仅截取开头120字符。摘要可帮助定位候选消息，但消息中段也可能包含相关内容。

后续记录增加结尾和总长度，从 DSH 原始请求提取文本，并区分已知处理规则与未知内容。报告时还需要保留请求标识和插件版本。

## 5. 原实现调整

调查后增加密集分隔处理和 `channelPerturbation` 策略，默认 `failure`，并为两区域传入配置。原测试记录为渠道相关80项通过，全套2137项通过、2项按平台跳过。

5.8.1的记录进一步增加 `breakIdentityClauses()`。10818字符提示的定向处理约增加28字符、0.26%字节，密集处理的对照增量约70.7%。分别检查各规则再次执行后是否保留原结果，避免已有分隔字符阻止其他适用规则执行。

对应13项身份说明测试加入后，全套记录为2218项通过、2项跳过，类型检查和构建通过。后续代码已继续变化，现有调用链与历史数据分别核对。

## 6. 维护要求

处理规则需要明确可修改的消息字段，检查工具参数及工具结果的保留情况。变换测试除单请求外，还应覆盖多轮前缀稳定性、角色范围和中止后的调用次数。

实际模式、重试结果和错误摘要应与发出的请求一致。详细设计见 [DESIGN.md](DESIGN.md)，后续对照见 [PINNED-11128-RETRY.md](PINNED-11128-RETRY.md)。

## 渠道错误诊断补充（5.18.1）

错误摘要展示首次请求的消息开头与结尾。首行标记只说明已知客户端标识的匹配情况，排查原因还需核对正文。若重试已为所有相关消息添加中性提示，报错会列出这一步的执行情况。测试见 tests/issue213-channel-evidence.spec.ts。
