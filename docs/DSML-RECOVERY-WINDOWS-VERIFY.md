# Windows DSML恢复验证

本文记录3.3.0及相关提交 `99cff6d`、`5c7200d`、`13da588` 的验证步骤。目标是检查模型将工具调用写入正文时，shim是否将可识别的调用转为结构化工具请求。

## 1. 准备构建

在独立源码目录运行依赖安装、构建及测试，记录提交和版本。原CI记录为Windows与Ubuntu均通过，Windows814项。

```powershell
pnpm install --frozen-lockfile --ignore-scripts
pnpm run check
```

## 2. 安装与加载

确认目标profile和已安装插件的绝对路径，备份该插件，再部署构建文件。校验源目录与部署目录的文件内容，重启DSH后检查新进程及插件加载。

静态脚本可检查恢复模块与接入位置：

```powershell
node scripts/verify-dsml.mjs
```

## 3. 实际工具调用

在测试会话选择WorkBuddy模型，发送需要执行工具的任务。检查实际工具执行结果、结构化调用记录和最终正文。

可使用仅输出标记的shell命令，避免对项目文件产生修改。保存执行输出及会话事件作为证据。

## 4. 网关与shim对照

以下操作会发送请求，执行前需要确认所用账号和费用：

```powershell
node scripts/verify-dsml.mjs --live 3
node scripts/verify-dsml.mjs --live 3 --through-shim
```

直连结果表示上游输出，经过shim的结果表示客户端接收内容。对比各轮的标记、原生调用、纯文本及空输出分布。

## 5. 判定条件

完整且工具名属于本次声明的invoke块应转为工具调用。缺少可识别工具名的片段按原输出处理；5.12.2后对唯一近似名称有受限恢复规则，具体条件见源码和测试。

模型是否输出标记可能随请求变化。原测量出现过一组6/6泄漏及另一组3/3原生结果，单轮输出应与接入路径和可恢复条件一起判断。

## 6. 保存结果

分别记录构建结果和部署校验，并记录进程开始时间、工具真实执行结果、直连和shim分布。出现合法invoke块仍留在正文时，保存脱敏后的原始响应及请求工具声明，供解析器复查。
