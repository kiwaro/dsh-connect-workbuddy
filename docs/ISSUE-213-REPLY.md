# issue #213：渠道拒绝的错误说明

本页保存对 issue #213 的回复草稿及当时的调查结论。文中的版本、提交和 npm 状态属于该次调查，不能作为当前发布状态。草稿尚未在本轮对外发送。

## 1. 请求已经经过哪些处理

报告将错误摘要中的 assistant 消息与会话日志中的 reasoning 文本对应起来，说明这些文本进入了请求。仅凭首行摘要，还不能判断网关实际匹配了哪段内容。

`UNAPPROVED_CHANNEL_OPENINGS` 用于首次请求的已知前缀检查。首次请求被拒绝后，`forceNeutralHead()` 按角色处理所有非空文本段：system、assistant，以及转换为 system 的 developer 消息都会添加中性提示，不要求命中该前缀名单。

```ts
if (!scansOpening(message['role'])) continue
if (content.trim() === '' || startsWithNeutralHead(content)) continue
message['content'] = `${WORKBUDDY_FALLBACK_SYSTEM_PROMPT}\n\n${content}`
```

该处理来自提交 `461ca3c`，调查时核对的标签从 v4.15.1 起包含这一提交，因此所查 5.11.0 版本也有此逻辑。报告中的错误还记录了强制中性提示、不可见扰动和密集扰动均已执行。由此可知，失败不能简单归因于“这些消息没有命中名单，所以未加中性提示”。

## 2. 错误摘要的歧义及修正

`channelEvidenceText(raw)` 读取 DSH 的原始请求，以便显示消息原有的开头。它不显示重试时添加的中性提示。旧文案未区分这两份请求，使首行标签看起来像是对全部处理过程的判断。

提交 `713437d` 修改了三处说明：

1. 未命中名单的标签明确限定为首行，不能据此判断整条消息是否经过处理。
2. 匹配说明同时提及前缀和正文子串。该描述依据 issue #125 的历史对照，不代表已确认所有网关规则。
3. 删除仅凭未知首行就建议修改 DSH 或其他插件提示的结论。

只有 `retriedWithForcedHead` 表明实际执行过相应重试时，错误才说明所有适用消息已添加中性提示。相关测试检查未执行该步骤时不出现此说明。

## 3. 尚未确定的拒绝原因

issue #125 的对照中，三个提示片段全部处理后请求返回 200。定向处理约增加 0.26% 字节。这只能说明所测样本的结果，不能证明其他提示形态均已处理。

本次错误包含 system 身份提示和三条 assistant 思考文本。添加中性提示后仍然被拒，可能涉及消息中段，也可能涉及消息结构或其他请求字段。现有摘要不足以区分这些原因。

报告建议发送历史前移除 reasoning 内容。这会改变发送给模型的上下文，是否有效仍需对照请求验证；不能称为唯一解决方法，也不能以未经测试的推测默认开启。若后续验证支持该方案，可另行设计配置开关。

## 4. 继续调查所需材料

当时错误摘要最多列出四条消息，每条仅含开头、结尾和长度。未列出的消息仍可能影响结果。可使用以下材料继续定位：

1. 脱敏后的完整失败请求，用于本地逐段对照。对外分享时先删除凭据、提示中的私人内容及账号信息。
2. 会话日志中其余消息的角色、长度和脱敏片段，用于确认摘要遗漏范围。
3. 如需增加失败请求留存功能，应单独实现默认关闭的配置，并说明保存位置、覆盖规则和清理方法。本文仅记录建议，现有 doctor 命令不因此具备该功能。

仅保留每条消息前后 200 字的材料适合初步定位，但不足以验证中段匹配。删除 reasoning 的对照也需要保留其他请求字段，以免把不同修改的影响混在一起。

## 5. 当时的交付范围

此次修改改善错误说明，没有证明 11128 已解决。调查记录称 `713437d` 已合并到 main、未包含在 v5.18.0 标签中，当时 npm latest 为 5.17.0；这些是历史状态。

子智能体跳过 `channel-continue` 的规则未修改。四条消息的摘要上限也未修改，继续定位时仍需补充第四节所述材料。
