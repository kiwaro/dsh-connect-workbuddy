# 渠道校验重试历史记录

本文整理截至2026-10-29关于HTTP400、业务码11128的处理记录。原“先重试”通知在5.13.0发布后存档，后续调查将固定提示与随回合变化的内容分别处理。

## 1. 分类与资料

排查时记录HTTP状态、业务码、错误类别、完整服务端提示及 `requestId`。11128可能涉及提示文本、会话标识及首条消息等不同检查，分类还需读取相应错误字段。

原issue #160中出现过 `channel_reject` 错误及 `You are a helpful assistant.` 摘要。该摘要取自处理后的请求，后续改为从 DSH 原始请求取证。

## 2. 请求内部重试

所述版本在同一账号依次尝试中性开头、稀疏分隔字符和密集分隔字符。成功形态可在进程内复用，具体选项由 `channelPerturbation` 控制。

固定system提示在新回合中仍可能保持相同。2026-10-29的记录中，相同body100次均返回400，修改三处短语后返回200。5.13.1开始在发送前处理已知固定提示。

`channelRejectContinue` 默认关闭，后续默认连续发送上限为1。它增加一个新回合及请求次数，适用条件需要根据失败内容是否变化判断。

## 3. 版本相关变化

| 版本范围 | 调查记录 |
| --- | --- |
| 4.13.2至4.14.1 | 原摘要采用处理后的body，尚缺后续三级重试 |
| 4.15.1至5.12.2 | 已有重试，但紧凑业务码匹配可能遗漏其他JSON形态 |
| 5.12.3 | 业务码分类改用共享读取器 |
| 5.12.4 | 密集处理采用线性扫描 |
| 5.13.1及后续 | 增加已知固定提示的发送前处理 |

原长度对照还记录了改写增加32字节和5行，以及摘要长度中另有11349的固定注入量。比较长度时需要注明所量的是 DSH 文本、请求文本还是错误摘要。

## 4. 执行耗时与中止

密集处理旧算法在92KB输入上记录为82.7秒，线性实现约10毫秒。请求中止检查保留原始错误并防止继续发送；相关对照见 [DESIGN.md](DESIGN.md) 和issue #159测试。

## 5. 报告内容

1. 已安装插件版本及加载方式。
2. HTTP状态、业务码、类别和请求标识。
3. 摘要所指消息角色及长度。
4. 是否只影响某个模型，以及是否发生模型繁忙或排队。
5. 同一输入在不同请求形态中的对照结果。
