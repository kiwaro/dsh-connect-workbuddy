# 隐私与脱敏（Privacy）

> 本文档是 `dsh-connect-workbuddy` 的**唯一权威隐私规则**。修改截图、编写文档或 issue 回复、发布新版本前均须阅读。
>
> 隐私检查优先于功能交付。未脱敏内容一旦进入 GitHub 或 npm 发布包，可能长期保留于历史 tarball 和已克隆的 Git 仓库中，后续修订无法撤回所有副本。
>
> 本文档位于 `package.json` 的 `files` 白名单中，**随包发布**，作为对使用者的隐私处理承诺。

## 基本规则

**仓库与发布包均不得包含能够识别真实账号、设备或会话的信息；本文明确允许的公开身份信息除外。**

判断标准为内容是否能够关联到具体个人、账号、设备或会话。存在此类关联时，必须脱敏或删除。

## 1. 受管的内容面

本项目的隐私检查范围分为五类，**每类均须单独检查**，避免仅检查部分载体而遗漏其他内容：

| 类别 | 典型载体 | 是否进发布包 |
| --- | --- | --- |
| **截图** | `docs/assets/*.png`、`docs/pr188-mac-shots/*.png` | `docs/assets` 进；`pr188-mac-shots` 不进但仍在公网仓库 |
| **文档正文** | `README*.md`、`CHANGELOG.md`、`docs/**.md`、issue 回复草稿 | 部分进 |
| **设计稿 / 演示页** | `docs/*.html`、`docs/assets/*.html` | 不进入发布包，但位于公开仓库 |
| **测试夹具** | `tests/*.spec.ts` 里的 `uin` / `nickname` / 邮箱 | 不进入发布包，但位于公开仓库 |
| **构建产物** | `lib/*.js`（打包会把源码字符串带进去） | **进** |

> ⚠️ **「不进发布包」不等于「不暴露」**。`docs/pool-header-redesign.html` 不在 `files` 白名单里，
> 但该文件位于公开仓库的 `main` 分支，可通过 `git clone` 获取。**判断标准是「公网可读」，
> 不是「在 npm 包里」。**

## 2. 绝对禁止出现在仓库任何地方的内容

除本文明确列出的公开身份信息外，以下内容均禁止写入：

- **完整手机号**。任何 11 位中国大陆手机号，无论是否使用引号或代码块，也无论位于 `docs/`、`docs/audit/`、
  测试夹具、HTML 演示页、CHANGELOG 引用里。**这是本项目历史上真实发生过的一类泄露。**
- **完整邮箱**。维护者邮箱同样不得写入。Git 提交中的已有作者信息不构成再次引用的许可，
  但**正文、测试夹具和注释中不得再次出现真实完整邮箱**。需要举例时写成 `someone@example.com`。
- **真实 uin / uid / enterpriseId**。WorkBuddy 的 `uin` 是账号级持久标识符（一串 9–12 位数字）。
  测试应使用 `1`、`100000000001` 等明确的合成值，**禁止复制真实设备日志中的账号标识**。
- **access token / refresh token / cookie / `X-Device-Token`**。已过期的凭据及凭据片段同样禁止。
  需要举例时写 `at-fixture`、`token-alpha-old` 这类明显的假值。
- **本机绝对路径里的用户名**。macOS 的 `/Users/<用户名>/…`、Windows 的 `C:\Users\<用户名>\…` 均不得出现。
  文档中必须使用占位符：`/Users/<you>/...`、`C:\Users\<you>\...`、`<repo>`。
- **会话 id / 设备 id / 指纹**。`session-<uuid>`、设备指纹产物。需要说明时用 `<session-id>` 占位。
- **真实昵称**。上游返回的账号显示名（中文昵称形如「老+姓」，英文形如 `Lao` 前缀的拼写，
  以及「用户 + 一长串数字」这种自动生成名）出现在截图或文档里，可能暴露参与插件测试的账号身份。
  版权行里的 `Copyright (c) 2026 LaoDing` 是**许可证主体**，不受此条约束（见 §5）。

## 3. 截图规则（历史泄露问题较集中的类别）

### 3.1 使用不可逆的脱敏方式

- ✅ **不透明纯色块覆盖**。覆盖后不得保留原始文字像素，并应使脱敏区域清晰可辨。
- ✅ **裁掉整个区域**。账号列、余额列可以整列裁掉，只要截图仍能说明问题。
- ❌ **马赛克 / 像素化**。小色块（≈4–10px）在马赛克边缘仍可能残留字形轮廓；而且本项目历史上用过
  **半透明**的马赛克（最暗处 199/255，不是黑），意味着遮罩仍保留了原始像素信息，存在泄露风险。
  以后一律不再使用马赛克。
- ❌ **高斯模糊**。小半径模糊是可以被反卷积攻击的；而且看不清的字形仍可能泄露字符数、词长。
- ❌ **半透明遮罩**（`opacity < 1` 的方块、带 alpha 的 PNG 矩形）。

### 3.2 检查截图边缘

**局部裁切不能替代完整脱敏。** 历史问题包括：截图的画板顶边曾残留部分账号号码。
号码仅被部分裁切，剩余字形仍可读，但图片的 `alt` 文案被标注为“无账号信息”。

规则：

- 截图前把**画板上边缘、下边缘、左右边缘各留 8px 空**，不要让任何内容贴在边上。
- 出图后**逐边检查**：把图放大到 400%，检查四条边是否残留部分裁切的文字。
- 包含真实账号表格时，优先替换为合成数据或完整排除该区域，避免逐行遮盖时遗漏。

### 3.3 复核脱敏成品

图片修改后必须**打开成品进行人工复核**，不能仅查看源文件或命令行输出。检查项包括：

- [ ] 所有真实账号名、手机号（含掩码形式 `1XX****XXXX`）、uin、昵称都不可读
- [ ] 没有残留的「半截字」贴在画布边缘
- [ ] 图片的 `alt` 文案与图里**实际**有没有账号信息**一致**（写着「无账号信息」就必须真的没有）
- [ ] 图片元数据干净（见 §4）

> ### 整窗截图的左下角账号信息
>
> 账号表格完成脱敏后，DSH 侧栏左下角的头像与昵称仍可能保留。该区域独立于账号表格，必须单独检查。
>
> 整窗截图（包括 DSH 及其他 Electron 应用）必须检查以下四处：
>
> | 位置 | 里面有什么 | 处理 |
> | --- | --- | --- |
> | **左下角** | 登录用户的头像与昵称 | **必须覆盖**，避免公开账号身份 |
> | **左栏工作区列表** | 项目目录名 | **默认覆盖**；确属截图说明对象时记录保留理由 |
> | **左栏会话标题** | 历史会话标题，可能包含工作内容 | **默认覆盖**；例外须记录理由 |
> | **窗口标题栏 / 顶栏** | 可能包含用户名或主机名 | 必须覆盖 |
>
> 文本扫描无法代替图片复核，必须打开成品检查这些区域。
>
> **已记录的保留例外**：`docs/pr188-mac-shots/` 那五张截图保留了左栏的工作区名与会话标题。
> 这些区域用于证明侧边栏是否出现 WorkBuddy 入口，完整覆盖会失去对应验证依据。该保留范围已明确记录；
> 同类例外必须在 CHANGELOG 中说明依据与范围。

> **真实号码的掩码形式同样必须覆盖。** `1XX****XXXX` 虽然只有 3+4 位可见，但它与 `tests/` 里的固件、
> CHANGELOG 里的引用一交叉就能定位到具体账号；而且截图里的掩码旁边往往还有余额、过期时间构成的指纹。
> **统一使用不透明纯色块完整覆盖。**

## 4. 图片元数据

PNG 的 `tEXt` / `iTXt` / `zTXt`、JPEG 的 EXIF / XMP 都可能带上拍摄设备、用户名、绝对路径。
历史检查结果不能覆盖新增或替换图片。每次变更后都须重新检查：

```bash
node scripts/check-pii.mjs          # 会列出每张图的元数据块
```

含 `tEXt` / `EXIF` / `XMP` 的截图必须先用工具剥离元数据再入库。

## 5. 允许存在的「本人信息」

下面这些是**有意公开**的，不算泄露，不得作为隐私清理对象删除：

| 内容 | 出现位置 | 为什么允许 |
| --- | --- | --- |
| `Copyright (c) 2026 LaoDing` | `LICENSE`、README、`package.json` 的 `copyright` 字段 | MIT 许可证主体，是法律声明 |
| GitHub 账号 `dingminhua` | 仓库地址、徽章 URL、issue 链接 | 项目公开身份，本来就在 URL 里 |
| npm 包名 `@dmh2002/dsh-connect-qoder` 等**其他包**名 | CHANGELOG 引用 | 是包名不是账号凭据 |
| `someone@example.com`、`/Users/<you>` 等占位 | 文档示例 | 显然是占位 |

> 区别在于：**「签名 / 署名 / 包名」是有意公开的身份；「账号凭据、手机号、uin、会话 id」是意外泄露的痕迹。**

## 5.1 三条已确定的适用边界

以下三项明确既有边界，后续修订须保持一致：

**① 维护者本人的昵称可以与余额同现。** 历史 CHANGELOG 中已有维护者本人昵称与金额同时出现的记录。
此类组合可能关联到账号，正是 §3.3 要求检查的内容。此记录仅涉及维护者本人，且该名称也是
许可证主体。**决定：允许，仅限维护者本人；任何其他账号的昵称都不许与金额同现。**

**② 反例固件不许写成可复制的真值。** 扫描器需要验证规则能够检出违规内容的样本；使用真实账号号码作为样本会使测试文件本身包含隐私信息。**决定：测试里的反例一律在运行时拼接**
（`['138', '1234', '5678'].join('')`），`allow` 里只放行结构上不可能是真号的值。

**③ 扫描器自身的注释可以用假值举例。** 注释需要说明被检测内容的格式特征。
**决定：可以，但用全零尾或单调数字这类明显假值，且不为它开任何文件级豁免。**

## 6. 发布前的强制核对
**这一步是发布流程的一部分，写在 [`RELEASING.md`](../RELEASING.md) 第 2.7 步，不得跳过。**

```bash
node scripts/check-pii.mjs
git log --format=%B origin/main..HEAD | node scripts/check-pii.mjs --stdin   # 提交信息
```

脚本退出码非 0 时禁止发布。检查范围包括：

1. 发布包内的每个文本文件（`files` 白名单）
2. **仓库内全部文本文件，隐藏文件包含在内**（`.env`、`.npmrc`、`.vscode/` 等目录或文件可能被误提交），
   按 BOM 自动解码 UTF-16
3. **PNG 与 JPEG 的元数据块**（`tEXt`/`iTXt`/`zTXt`/`eXIf`、EXIF/XMP/COM）
4. **文件名**。文件名中的真实号码及部分掩码也可能泄露身份；合成占位符除外
5. `screenshots.json` 的登记

匹配前会先做归一化（全角转半角、去零宽字符），所以带连字符的、带 `+86` 前缀的、
全角数字等写法会按同一规则匹配，改变格式不能代替脱敏。

**自动检查存在以下限制，须补充人工核对：**

- **图片内容**。文本扫描不能充分识别截图中的可读信息，须按 §3.3 人工复核。
- **新出现的形态**。规则基于已知泄露类型，可能无法识别新增类型。
- **超过一周的提交信息**。扫描器不自动读取 `git log`，须通过上面的第二条命令补查；检查结果仅覆盖执行时的提交范围。

出现**误报**时，应将样本替换为明确的合成值，或在 `allow` 中精确放行
**并同时增加反例测试**。不得通过删除或放宽检测规则处理误报。

## 7. 泄露处理

1. **修正当前文件并提交**，避免在说明中再次引用真实值。
2. **由维护者发布修正版**。旧包仍可能被下载，新版本只能更新最新版入口；
   要发新版本必须在 `CHANGELOG.md` 里**如实写明泄露了什么**（不得以“若干文档修正”等笼统表述代替）。
3. **历史清理必须记录并取得授权**。历史提交（`git log -p`）仍然能查到；如果确实需要清理，
   用 `git filter-repo` 重写并强推，历史重写须另行取得授权，并在 CHANGELOG 与 Release 中说明处理范围。
4. **按实际泄露范围处理凭据**：正常运行的凭据文件位于 DSH 用户目录（`$DSH_HOME/workbuddy-vault/` 与
   `~/.dsh/.workbuddy-auth.*.json` 都在 gitignore 之外的用户目录）。不能仅凭显示名和号码泄露就断定凭据也已泄露。
   如确认 token 曾进入仓库，必须优先轮换凭据。

## 8. 写给 AI 助手

AI 生成的文档和操作结果同样需要验证，不能以助手的完成声明代替检查：

- 让 AI 写任何含「真机」「实测」「截图」的内容时，**明确要求它只写占位符**。
- AI 生成的文档入库前，**自行执行一次 `node scripts/check-pii.mjs`**，不得仅依据助手的完成声明。
- AI 代跑发布时，[`RELEASING.md`](../RELEASING.md) 第 2.7 步**必须**由人确认结果，不能以助手的完成声明代替人工确认。
