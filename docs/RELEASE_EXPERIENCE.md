# 发布操作记录

本文汇总 2026-10-13 在 macOS 上观察到的 npm 授权、日志和构建检查行为。发布步骤见 [RELEASING.md](../RELEASING.md)。其中的时长来自单机小样本，复查时应记录 npm、Node.js、操作系统和账号配置。

## 1. 记录依据

本文按依据记录验证范围，包括实际执行和源码阅读，也注明小样本观察及缺少验证的结论。2FA 的两组对照发生在同一维护账号发布 `dsh-connect-qoder` 0.4.3 时；本项目使用该账号和同类工具，因此保留这份排查材料。

## 2. 浏览器授权

所读 `npm-profile/lib/index.js` 的 `webAuthCheckLogin()` 使用 `GET /-/v1/done?authId=…` 查询授权。返回 202 时按 `retry-after` 等待，返回 200 后继续上传，返回 404 表示授权会话失效。

历史对照如下：

| 会话 | 轮询次数 | 末次响应 | 结果 |
| --- | --- | --- | --- |
| 由助手转发验证链接，再等待人工操作 | 约 92 次（≈4.6 分钟）后耗尽 | `GET 404` | `PUT 401`、`exit 1`，真失败 |
| 维护者在自己的终端里跑 | 13 次（约 49 秒） | `GET 200` | `PUT 202`、`exit 0`、`+ …@X.Y.Z` |

该记录中，轮询间隔约 3 秒，超时约 4.6 分钟。维护者在交互式终端执行并及时确认浏览器授权的过程约为 49 秒。排查这类问题时，应先检查授权是否完成，再查询包是否已经公开。

## 3. 日志归属与保存

npm 将授权 URL 及其中的 `authId` 记录为 `***`。对应核对运行记录时，先用日志时间和终端历史匹配发布操作，再检查轮询次数与末次状态。

| 检查对象 | 材料 |
| --- | --- |
| 授权是否完成 | 轮询末次响应及退出结果 |
| 是否进入上传 | PUT 请求状态 |
| 版本是否公开 | registry 的版本条目、发布时间和包校验值 |
| 由哪次终端操作触发 | 日志时间与终端历史 |

当时 npm 使用 `logs-max:10`，后续命令会轮转旧日志。需要长期保留的状态行和退出结果应在检查后保存。部分失败日志已轮转删除，成功日志标识为 `2026-10-13T05_57_00_212Z`。

## 4. 构建文件检查

构建器可以提升正则或重命名变量。检查发布包时，应结合运行时导出值、行为测试和 tarball 校验值。源码字面字符串适合定位实现，运行结果用于判断包的行为。

本项目的 `WORKBUDDY_CONNECT_VERSION` 通过 `tsdown.config.ts` 注入。修改版本后需要重新构建，发布前的 `prepack` 会执行相应步骤。

## 5. 发布协作

发布前由获授权的执行者完成代码检查、版本记录、Git 提交与 tag 核对。维护者使用自己的交互式终端完成 npm 登录、发布及浏览器确认，再核对 registry 和 GitHub Release。

记录中的助手代执行尝试为 4 次，约耗时 20 分钟，产生 3 条失效授权链接；维护者直接执行的一次在 49 秒完成。该材料说明授权等待需要计入执行安排。

## 6. 适用范围

这些观察发生于 macOS 和特定 npm 版本。Windows 浏览器启动及授权过程需要单独记录。原始失败日志已部分缺失，时长与次数按当时留下的记录引用。
